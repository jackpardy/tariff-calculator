# Why

Student trampoline rules change from season to season and from one
competition to the next. So a coach must be able to write or adjust
requirements in the app, without code changes, and share them. Built-in
requirements are a convenience, not the main path.[^adr-0003] ADR 0003 is still
marked *Proposed*, although everything below is implemented.

In the app these are always called **requirements**. "Set" means a set
(compulsory) routine. The Go type is still `requirements.Set` (see the
[glossary](../glossary.md)).

# The format

A list of requirements is plain JSON, so it can be stored, exported, imported
and shared as a file, as pasted text, or [by link](../features/sharing.md):

```json
{
  "format": 1,
  "name": "BUCS L1 · first exercise",
  "description": "Voluntary first exercise. ...",
  "source": "BUCS Trampoline and DMT Championships 2026: Competition Structure (version 1)",
  "rules": [
    { "type": "elements", "min": 10, "max": 10 },
    { "type": "different", "label": "10 different elements: none repeated" },
    { "type": "count", "label": "At least 9 somersaults of 270° or more",
      "match": { "rotation": { "min": 3 } }, "min": 9 }
  ]
}
```

`format` is versioned (currently 1) so old files can be migrated later.
`requirements.Parse` rejects unknown fields, so typos in hand-written files
are caught, and `Validate` reports every problem, one per line. The rule types
and matchers are described in [rule types](rule-types.md).

## Scoring

Requirements also say how routines checked against them are scored. These
settings are the starting point for the routine's
[checks](../features/routine-builder.md#checks), which a coach can override for
one routine:

| Field | Meaning | Typical use |
|---|---|---|
| `no_difficulty` | Difficulty isn't scored | Set routines; FIG AG1/AG2/Junior first exercises |
| `repeats_allowed` | Elements may repeat | Set routines |
| `scored_elements` | Only the *n* highest (or chosen) elements score | AG3 and BG 17–21 first exercises (2) |

# Evaluation

`requirements.Evaluate(set, routineValidation)` checks **every** rule and never
stops at the first failure. For each rule it returns pass or fail, a
description (the author's `label`, or plain English generated by `Describe`), a
detail such as "found 0", and the element numbers involved.

- Rules look at the routine as written. The exception is `difficulty`, which
  uses the counted total from [routine validation](../domain/routine-validation.md).
- `RequiredElements` lists the elements that satisfy a requirement. The
  [tariff sheet](../features/tariff-sheet.md) ticks these in its Req. * column.

# Where requirements live

| Kind | Stored | Referenced as |
|---|---|---|
| Built-in | JSON embedded in the binary, `requirements/sets/<group>/<id>.json` | `builtin:<id>` |
| Custom | The browser, `localStorage['trampolineRequirementSets']` | the saved id; the server is sent the JSON |

A routine stores which requirements it is checked against. The page posts the
built-in reference or the custom JSON with every render, so the server stays
stateless. When accounts arrive, the same JSON moves into a database.

## Built-in requirements

A built-in is only added from a **cited source** (rule book, handbook or
competition document). Its `source` names that document and the season.
`sets/groups.json` names and orders the groups. The loader panics at start-up if
a file is missing, unlisted, listed twice or invalid, and the tests fail the
same way. The app tells users to check built-ins against the current rules.

| Group | Concept |
|---|---|
| ISTO, Irish Student Trampoline Open (2025) | [ISTO](isto.md) |
| BUCS student championships (2026) | [BUCS](bucs.md) |
| FIG age groups (2025–2028) | [FIG age groups](fig.md) |
| British Gymnastics national pathway (2026) | [BG national](bg-national.md) |
| British Gymnastics club & regional pathway (2027) | [BG club & regional](bg-regional.md) |

Gymnastics Ireland levels are waiting for documents (see
[open questions](../open-questions.md)). Requirements that are a single fixed
routine are listed apart as [set routines](set-routines.md). Each group's
requirements are also paired into [levels](levels.md), one per competition
level, so a gymnast's two exercises are checked together.

# The editor

The requirements page (`GET /requirements`) lists the built-in and saved
requirements. A saved one can be opened, duplicated (including from a
built-in), deleted, exported as JSON, imported, or shared. The editor follows
the skill editor's pattern ([rendering](../architecture/rendering.md)): the
browser posts the form to `POST /requirements/editor`, the server parses and
validates it into the model and re-renders the editor with any problems listed,
and the browser saves the result. Validation exists only in Go.

A valid set is also checked for rules that can't be met
(`requirements.Conflicts`, `requirements/conflicts.go`), shown as **These can't
all be met** without blocking the save. It tests each skill description
against a broad sample of real skills (every rotation, twists up to 4, each
take-off, shape and direction), and flags:

- a description no skill fits, where an element is needed;
- more elements, a later position, or more special requirements than the
  routine's length allows (number-of-elements rules, a set routine, or 10);
- number-of-elements or difficulty minimums above their maximums;
- a needed element that "every element must…" rules out, or two such rules
  with nothing in common;
- more needed of a kind than a count rule allows (a required double back where
  doubles are banned);
- more needed of a skill than exist without repeating, when repeats aren't
  allowed;
- two rules for the same position that no skill meets both of;
- a difficulty minimum above what the longest routine of the hardest allowed
  (or capped) elements reaches.

It catches the obvious cases, not all: a set with nothing flagged may still be
impossible. Every built-in set is tested to have no conflicts.

Set routines aren't written in the editor: it doesn't offer "Set routine" as a
kind of rule, and shows an existing one's elements read-only. They're built in
the Routine Builder ([set routines](set-routines.md#writing-one)).
